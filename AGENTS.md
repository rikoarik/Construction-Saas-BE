# Backend Agent Rules

This repository contains **backend core and Telegram Bot as separate lanes**.

Route work by task prefix:

- `BE-*` -> read `docs/backend/BACKEND.md`, `docs/delivery/BACKEND-TASKS.md`, and `docs/backend/BACKEND-ACCEPTANCE.md`.
- `BOT-*` -> read `docs/bot/BOT.md`, `docs/delivery/BOT-TASKS.md`, and `docs/bot/BOT-ACCEPTANCE.md`.

Shared backend references live in `docs/architecture/`, `docs/specs/`, and `docs/product/PRD.md`.

Hard rules:

- PostgreSQL is authoritative storage; no Supabase dependency;
- tenant isolation and authorization are backend responsibilities;
- progress/RAB/approval calculations live in backend core only;
- Telegram Bot is an adapter, never a second business-logic implementation;
- bot code must not directly recreate or bypass domain rules;
- financial/quantity values use precise decimal/numeric semantics;
- approved progress is audit-safe and idempotent;
- API/worker mutations use explicit transactions where invariants span writes;
- changes to canonical contracts are reviewed before consumer changes;
- do not mark tasks done without repository evidence/tests.

For parallel sessions follow `docs/delivery/PARALLEL-WORKFLOW.md` and respect lane ownership.
## Git Commit Attribution

- Commit messages must be written as normal human project commits.
- Do not add `Co-Authored-By` trailers for Claude, AI tools, agents, or models.
- Do not add `Generated with Claude Code`, `Generated by AI`, or similar attribution.
- Do not add Claude session URLs to commits or pull requests.
- Preserve the repository's configured Git author identity.
- Never modify `git config user.name` or `git config user.email`.

## Task Execution & Git Workflow

### Mandatory Task Workflow

- Execute tasks sequentially based on their dependencies.
- Work on one task at a time.
- Read the relevant task specification and acceptance criteria before implementation.
- Do not skip tasks unless blocked by an unresolved dependency.
- Do not combine multiple completed tasks into one commit.
- Never mark a task as completed before verification.

### Automatic Commit & Push

After completing EACH individual task, the agent MUST:

1. Verify the implementation against the task's acceptance criteria.
2. Run relevant tests, lint, type checks, and build checks.
3. Fix any failures before proceeding.
4. Update the task status in its corresponding TASKS.md file.
5. Review changed files using `git status` and `git diff`.
6. Stage only files related to the completed task.
7. Create a Git commit.
8. Immediately push the commit to the current remote branch.
9. Verify the push succeeded.
10. Automatically continue to the next available task.

Do not wait for user confirmation between tasks.

The user explicitly authorizes automatic commits and pushes
after each successfully completed task.

### Commit Message Rules

Use Conventional Commits:

- feat(scope): description
- fix(scope): description
- refactor(scope): description
- test(scope): description
- docs(scope): description
- chore(scope): description

Examples:

feat(auth): implement company authentication
feat(projects): add project management endpoints
feat(bot): implement Telegram report submission
feat(rab): add budget import interface

Commit messages MUST:
- Be concise and human-readable.
- Describe actual changes.
- Never contain `Co-Authored-By` attribution for AI agents.
- Never contain `Generated with Claude Code`.
- Never contain `Generated by AI`.
- Never contain AI signatures, promotional footers, or session URLs.
- Never add Claude, OpenCode, or other AI tools as contributors.

Preserve the existing Git author identity.

Never modify:
- git config user.name
- git config user.email

### Git Safety

- Never use force push.
- Never reset or overwrite unrelated changes.
- Never stage unrelated files.
- Never amend unrelated commits.
- Never switch branches without a valid reason.
- Push only to the current task branch.
- Never create pull requests unless explicitly requested.
- Never merge branches automatically.
- Never push secrets or environment credentials.

If tests fail, fix the implementation before committing.

If pushing fails, report the error and resolve it safely.
Do not claim that changes were pushed successfully.

### Continuous Task Execution

The agent MUST continue working automatically:

Read task → Implement → Test → Update status
→ Commit → Push → Next task

Do not stop after successfully completing one task.

Continue until:
- All tasks are completed.
- A critical blocker prevents further progress.
- User intervention is required.
- The user explicitly requests a stop.

### Task Ownership

Frontend repository:
- Follow FRONTEND-TASKS.md.
- Implement frontend and Telegram Mini App tasks only.

Backend repository:
- Follow BACKEND-TASKS.md and BOT-TASKS.md.
- Implement Go backend and Telegram Bot tasks only.

Never implement responsibilities belonging to another repository.
